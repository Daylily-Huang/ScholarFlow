## 4. F01：不要把文本命中升级成科学命题支持

位置：`shared/execution/debate_handoff.py:204` 的 `_compare()`、`:437` 的 `to_evidence_link()`。

### 已复现现象

命题均为 `roads reduce gene flow`：

| 引句 | 当前结果 | 问题 |
|---|---|---|
| `roads` | `VERIFIED / EXACT` | 一个实体词不支持完整命题 |
| `It is not true that roads reduce gene flow.` | `VERIFIED / EXACT` | 否定句被升级为支持 |

同一用例还带 `claim_status=unsupported`、`location={"page": null}`，且缺少 `artifact_ref`、`checked_scope`，仍得到 `problems=[]`。

根因：双向子串判断 `p in q or q in p` 及词面覆盖率仅判断字符/词出现，不判断否定、对象、条件和关系。记录入口没有真正强制检查其文档所要求的 `checked_scope`，也未校验上游审计状态。

### 修改步骤

1. 将 `_compare()` 的结果降格为 `text_match`，禁止仅凭 EXACT/OVERLAP 设置语义 `VERIFIED`。
2. `to_evidence_link()` 先验证可解析的产物引用、稳定证据 ID、有实质内容的定位、检查范围、上游审计状态。空对象、空页码不算有效定位；不强制所有来源必须有 PDF 页码，可接受经验证的段落/表格锚点。
3. 区分“原文中存在引句”和“引句支持当前命题”。后者需要带出处的结构化判断：对象、关系、方向、条件、研究设计与适用范围。
4. 可用 Agent 进行语义判断，但须记录原文、理由与不确定性；无法可靠判断时保持待核验。简单否定词过滤只能作为告警，不能宣称解决全部语义问题。
5. 对上游 `unsupported` / `unverified` 记录默认不得自动升级；如需复核改判，必须产生新的审计记录，而不是覆盖历史状态。
6. 跨语言变体增加规范化去重与来源记录；“两条译法”不等于两份独立证据，不应仅凭数量升级。

验收：上述两反例不得 VERIFIED；缺检查范围/无效定位/失败审计均被阻断；同实体不同方向、不同物种、不同条件的反例覆盖；真正支持且来源完整的正例仍可通过。

## 5. F02：数值核验必须绑定值、单位和所在证据片段

位置：`skills/literature-evidence-extraction/scripts/quote_audit.py` 的 `extract_value_tokens()`、`:193` `check_value_alignment()`、`:249` `audit_evidence()`、`:350` `gate_failed()`。

### 已复现现象

| 用例 | 当前结果 |
|---|---|
| 原文 `55.4%`，抽取值 `5.4%` | `ALIGNED`，strict 门禁不失败 |
| 值 `5.4%` 只出现在距离引句很远的其他上下文 | 报 `NOT_IN_QUOTE_CONTEXT`，strict 门禁仍不失败 |
| 原文反应体积 `20 microliters`，抽取为 `999 microliters` | `value_checked=0`，strict 门禁不失败 |

### 修改步骤

1. 不再用任意子串匹配数值。解析数值边界，保留正负号、百分比、科学计数法和单位；`5.4` 不得命中 `55.4`。
2. 利用字段 Schema 确认哪些值是数值字段，覆盖整数体积、温度、样本量等，不因担心年份/引文而跳过全部裸整数。
3. 单位转换采用显式规则和转换记录；不得简单删除 `%` 就当相同。
4. 默认将 `NOT_IN_QUOTE_CONTEXT` 设为待核验并阻止该记录进入 confirmed 输出。全文命中只能用于寻找候选来源，不能替代当前字段的证据锚定。
5. 表格值跨行列或正文引用表格时，允许独立证据锚点，不机械限制为 ±200 字符；记录表号、行列标题、脚注和原始值。
6. 汇总状态与 CLI 退出码共用一个判定函数，避免 `summary.gate_failed` 与实际出口分歧。
7. 派生值单走公式、输入证据 ID 与重算核验路径；不要求派生结果数字必须直接出现在原文。

验收：上述三反例均不可作为已核验结果交付；增加负数、百分比/比例、范围、科学计数法、单位换算、表格邻行错配、派生值正例。

## 6. F03：损坏日志恢复后不能继续在坏尾部追加

位置：`shared/execution/session_store.py:83` `append_event()`、`_read_events()`、`_quarantine_tail()`。

复现步骤：写入正常 E1 → 模拟崩溃留下 `{"event_id":` 半行 → 调用 `append_event(E2)`。当前返回 `True`，恢复后只读到 E1。原因是隔离仅复制损坏尾行，没有从活动日志解除坏尾部，新事件拼在坏尾部后被一起忽略。

### 修改步骤

1. 检测到坏尾部后，默认暂停追加并返回明确的 `RECOVERY_REQUIRED`；或在明确的恢复事务中完成修复后再追加，不能继续直接写。
2. 保留原始日志和坏尾部证据，校验有效前缀，原子生成恢复后的活动日志；记录恢复原因与文件摘要。
3. 修复操作可重复执行，同一损坏不应每次读取都产生新的隔离副本。
4. 新事件只有在有效 JSONL 边界上持久化成功后才返回成功；按持久化要求决定是否增加 flush/fsync。
5. 中段损坏继续保持停止，不要自动猜测删行。

验收：无换行半行、有换行坏行、重复恢复、修复期间异常、修复后追加再重启；已返回成功的 E2 必须可恢复，或追加调用必须明确失败。不得以忽略异常实现“成功”。

## 7. F04：同一个事件 ID 不等于同一个状态

位置：`shared/execution/session_store.py:190` `rebuild()`、`:211` `save_snapshot()`、`:230` `consistency_report()`。

复现：事件 E1 将 state 设为 WAITING_USER；快照保留 `last_applied_event_id=E1` 但 state 为 CLOSED。当前报告 `consistent=true`，重放实际却变回 WAITING_USER。

另有实现/注释冲突：`save_snapshot()` 注释宣称自动写 CHECKPOINT 事件，当前函数仅保存快照。

### 修改步骤

1. 明确唯一写协议：业务状态变更先提交事件，再从事件投影生成快照。不能把任意完整对象快照写入当成业务提交。
2. 校验规范化业务投影或状态摘要，而不只比较末尾事件 ID；差异报告至少列出不同字段。
3. 建立可信起始状态/检查点与事件序号绑定。不要把任意当前快照既当待检对象，又当全部重放的可信初始状态。
4. 快照中 revision、恢复诊断等非业务字段与业务投影分开比较。
5. 校验事件所属 session、事件类型及可投影 payload；修正 CHECKPOINT 注释或实现相应事件协议。

验收：同 ID 不同 state 必须不一致；同 ID 不同 ideas/decisions 也须检出；“事件已写、快照未写”的崩溃可恢复；同一日志重复重放结果一致。

## 8. F05：授权指纹缺失必须停止，而不是跳过比较

位置：`shared/execution/debate_handoff.py:147` `prepare_dispatch()`；对照 `skills/research-idea-debate/references/evidence_handoff.md:35`。

复现：合法 `gap_type=SEARCH_GAP`，但 approval 只有 `status=CONFIRMED`，没有指纹。当前 `dispatchable=true`。规程却要求“指纹缺失或不匹配回到 WAITING_GAP_CONFIRMATION”。

### 修改步骤

1. 在比较前先强制要求指纹存在；缺失返回 `APPROVAL_BINDING_MISSING` 并要求确认。
2. 确认记录必须能够回指实际用户确认事件，绑定会话、构想版本、问题范围、目标技能及预算；不只信任字符串 CONFIRMED。
3. 指纹不匹配、构想版本变化、预算变化均明确失效；历史缺失值不自动补成已确认。
4. 为派发定义幂等键，明确 IN_PROGRESS、COMPLETE 与显式重试的行为，避免恢复时重复启动。
5. 将这些检查放在最终可调用入口，不能只靠某个上游调用者偶然完成 Schema 校验。

验收：缺指纹/假确认事件/范围变更/版本变更均不能派发；未变且有有效确认的恢复可继续；相同幂等键不会启动第二次。本次只复现载荷门禁放行，未执行外部检索。

## 9. F06：数据修复不能制造用户授权

位置：`shared/execution/session_store.py:326` `heal_referential_integrity()`，特别是 `:349`。

源码会给缺失 gap 自动补占位对象，其中包含 `approval.status=CONFIRMED`、构造的 `EV-HEAL-*` 事件 ID 和 `fp-heal-*` 指纹；并默认关联第一个 idea、版本 1。

问题不是补占位本身，而是修复工具把未知关联与未知授权写成确定事实。当前假指纹通常会被派发指纹比较拒绝，因此这里不声称已证明其导致实际外部派发；但会污染授权记录和后续逻辑。

### 修改步骤

1. 自动补全仅生成“待修复占位”，approval 使用现有契约允许的 PENDING/INVALIDATED 等非已确认状态。
2. 不能确定 idea_id/version 时报告孤儿关系；不要猜第一条 idea。如果当前 Schema 不允许未知值，保持原状态并输出修复提案，而不是编造合法字段。
3. 将修复事件与用户授权事件分离；修复日志只能证明“发生了修复”，不能证明“用户同意派发”。
4. 从已有真实事件可无歧义重建时才恢复确认；否则等待用户。

验收：孤儿修复不新增虚假 CONFIRMED；不存在的 confirmed_event_id 不可通过校验；多构想会话不发生默认错绑。

明确冲突：

操作方案：

1. 唯一深度规则为：研究目标与资源深度正交；有效配置沿用，无有效配置展示三档并确认；标准档仅为推荐，不能由“开题”静默推导 Deep。
2. 四入口使用同一配置来源生成或校验模式表，避免手工复制多份默认值。
3. 未实现功能从正常交付承诺中移出，标为计划；若属于宿主人工执行能力，明确输入、执行责任和可验证输出，不能同时标为自动交付和 NOT_SUPPORTED。

5. Token/时间提供实测区间与假设，记录 actual/estimated/unknown；不能把篇数或主张上限当成实际计算费用保证。

验收：四入口无相互矛盾的默认档；每档承诺都能映射已实现能力或显式人工步骤；无有效配置不会自行启动；深度档不再无条件承诺未实现的敏感性分析。

## 12. F09：分离未知、未报告、证据方向与核验状态

抽取入口 `:17` 的“没有直接证据时输出 NR”过宽。未获取全文、尚未检查、仅引自其他文献、可重算派生值都不等于作者未报告。

讨论适配器把 CHALLENGE/BOUNDARY 全部设为 UNRESOLVED，是现行明示规则而非偶然实现错误，但会使“已经核实的反证”和“尚未判断的材料”混在一起。

建议契约方向（概念示例，不要求立即新增这些枚举）：

| 维度 | 回答什么 | 示例 |
|---|---|---|
| 获取/检查状态 | 能否看到、检查到了哪里 | inaccessible / unchecked / checked |
| 字段状态 | 原文怎么提供该字段 | reported / not_reported / cited_only / derived |
| 来源核验 | 引句和定位是否真实有效 | verified / unverified / failed |
| 命题方向 | 对当前主张有何关系 | support / challenge / boundary / context |
| 语义核验 | 这个关系是否已经核实 | verified / unresolved |

操作：先盘点现有枚举与消费者，尽量复用；必须扩展时进行版本化映射。NR 要带 checked_scope 和未报告原因；已核实反证可进入反证栏，但不得进入支持计数。缺证据既不能升为支持，也不能自动推断反对。

验收：全文不可得不输出“作者未报告”；明确反证可被核实且不计支持；派生值保留公式与依据；旧版消费者遇到新状态不得静默映射为 supported。

## 13. F10：把“测试通过”映射到真实能力

`docs/CAPABILITY_STATUS.md:4` 仍称“三个 Skill”的唯一权威说明；第四技能的授权、恢复、语义回流应纳入同一能力台账。已有状态也需定义清楚，例如 PARTIAL，以及 CODE_VERIFIED 究竟验证的是结构、流程还是科研正确性。

不建议手工到处加 `[TESTED]`，容易随代码更新失真。每项能力记录：实现入口、对应测试 ID、覆盖边界、最后验证提交、证据来源、未覆盖场景。

分层验收：

1. 结构：Schema、路径和字段。
2. 行为：失败门禁、授权、恢复、幂等、引用溯源。
3. 科研质量：真实论文金标的字段准确率、数值/单位正确率、主张与证据方向准确率。
4. 工作流：同任务、同模型和预算下的召回、交付质量、时间与 token。

本次 709 项测试属于“现有测试集合的执行结果”，不能替代第 3–4 层。先把 F01–F06 的反例转成回归测试，再增加有代表性的真实文献样本。金标由人工复核并保存判定依据；不要用同一 Agent 生成答案再自评分。

对于复用性，不一定要删除 shared 架构。可以提供“单技能入口 + 必要共享依赖”的安装包与依赖清单；仅复制一个 Skill 目录不能等价于完整安装。当前安装测试跳过，应在可用的隔离安装环境补验，而不是只改文档宣布支持。
