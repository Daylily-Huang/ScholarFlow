## 3. 必须继续修复的问题

### R01 / P1：研究问题仍被升级为已验证结论

位置：`shared/execution/debate_handoff.py:644`，以及 `_compare()`、`to_evidence_link()`。

输入引句：`We tested whether roads reduce gene flow.`；命题：`roads reduce gene flow`。即使提供有效页码和 checked_scope，该句也仅表示“研究是否如此”，并不报告结果。当前返回 `alignment=VERIFIED`、`quote_match=EXACT`、`problems=[]`；缺 artifact_ref 仍可如此。

根因：增加 `text_match` 字段和否定词过滤后，最终 alignment 依然取决于词面 supported。代码并没有新增必须通过的结构化语义核验。

修改要求：词面匹配只负责候选对齐；VERIFIED 必须另有可追溯的语义判断记录与来源核验。未完成语义核验时保持 UNRESOLVED。不能继续通过追加 whether 等关键词黑名单来宣称根治。

验收：研究问题、假说、他人观点、条件性陈述、被推翻的结论都不自动变成当前论文的支持；缺产物定位不能通过；来源完整且语义经核实的正例仍通过。

### R02 / P1：单位和符号仍被丢弃，裸整数未核验

位置：`skills/literature-evidence-extraction/scripts/quote_audit.py:180–210`。

已复现：

| 原文 | 抽取 | 当前 |
|---|---|---|
| `20 microliters` | `20 milliliters` | ALIGNED，strict 不失败 |
| `-5.4%` | `5.4%` | ALIGNED，strict 不失败 |
| 研究包含 20 samples | 数值 999 | value_checked=0，strict 不失败 |

关键源码：`:192` 仍执行 `v.add(m.group(1))`，与“不再退化成裸数”的注释相反；边界只检查数字字符，允许跨正负号匹配。整数数值类型仍不受字段级核验保护。

修改要求：删除带单位值的裸数替代；数值、符号、指数、单位整体解析；明确转换而非忽略单位；根据字段类型检查纯整数。新增上述三反例，并覆盖百分数/比例及合法单位换算正例。

### R03 / P2：文本开头的正确数值反而被拒绝

位置：同文件 `:197` `_token_present()`，特别是 `:210`。

原文与引句均为 `5.4% was the observed proportion in the sample.`，抽取 `5.4%`，当前报 NOT_FOUND_IN_SOURCE 并失败。

原因：文本开头 before 是空串，而 Python 中 `'' in '0123456789'` 为 True；因此 `before not in ...` 为 False。文本末尾也存在同类边界风险。

修改要求：显式区分“没有相邻字符”和“相邻字符是数字”，或采用完整数值词法解析。增加开头、末尾、整段仅为数值及括号包围正例，并保留防止 5.4 命中 55.4 的反例。

### R04 / P1：完整 JSON 缺换行后追加仍导致事件不可读

位置：`shared/execution/session_store.py:117`、`:171` 附近。

复现：事件文件只有合法 E1 JSON，但最后没有换行；`append_event(E2)` 返回 True；再读取事件得到空列表。两个 JSON 对象被拼在同一行，并被识别为坏尾部。与上次无效 JSON 半行不同，这次 `_read_events()` 成功解析 E1，所以不会触发新门禁。

修改要求：追加前同时核验 JSON 合法性和记录边界。对无换行末条明确执行恢复/补分隔协议或拒绝追加；不能拼接后再隔离。返回成功必须意味着 E2 可再次读取。

验收：完整 JSON 无换行、无效半行、有换行坏行三种情况分别测试；恢复后 E1、E2 均保留，不只是返回成功。

### R05 / P1：授权绑定没有验证实际事件，版本字段比较错误

位置：`shared/execution/debate_handoff.py:180`、`:224`。

输入合法指纹，confirmed_event_id 为不存在的字符串；approval.approved_idea_version=1，实际 gap.idea_version 从 1 改为 2；execution_status=RUNNING。当前仍 `dispatchable=true`。

原因：仅检查事件 ID 非空；版本循环读取的是 `gap.approved_idea_version`，而契约的当前字段是 `gap.idea_version`，两侧缺任一值就跳过比较。指纹本身也未覆盖该版本；派发仅对 COMPLETE 幂等，不对 RUNNING 阻断。

修改要求：从可信会话/事件存储加载真实确认事件，核验角色、会话、构想和范围；比较 approval.approved_idea_version 与实际 idea_version。缺必要绑定失败关闭。为 RUNNING 定义在途幂等拒绝和显式重试流程。

验收：分别独立测试假事件、变更版本、变更会话、RUNNING 重复请求，而非只验证组合输入。保持有效确认、未变版本的正例。本轮仅验证门禁载荷，没有真的派发任务。

### R06 / P2：孤儿修复产物不符合当前 Gap Schema

位置：`shared/execution/session_store.py:414`；`schemas/research_debate_gap.schema.json`。

两构想会话的孤儿 gap 修复返回 PENDING 占位是正确方向，但 Schema 实跑发现：缺 schema_version，idea_id=null 不符合 string，idea_version=null 不符合 integer，scope_fingerprint=null 不符合 string。即使只有一个构想，缺 schema_version 与空指纹问题仍需解决。

修改要求：不能为满足 Schema 回退到伪造确认或猜测归属。无法形成合法 GapRequest 时输出独立 repair proposal，不加入正式 gap_requests；或者版本化扩展 Schema，显式支持未绑定占位并同步所有消费者。

验收：修复输出要么完整符合当前契约，要么明确作为待修复提案返回；自动修复后立刻执行 Schema 校验；无真实确认不得派发。
