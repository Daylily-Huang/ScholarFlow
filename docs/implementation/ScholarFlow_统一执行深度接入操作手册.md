# ScholarFlow：快速／标准／深度统一接入操作手册

> 文档日期：2026-09-08。核对基线：本地提交 `78a32604f80a178a3f2bd70b77cf2698a8ff37b8`，版本 `0.6.5`。
> 本文是待实施设计，不代表下述功能已经实现；本次仅新增文档，没有修改三个 Skill 的运行代码，也没有核对远端是否存在更新提交。

## 1. 先明确要加的是什么

不是再加三个名称，而是加入一套贯穿整个流水线的“执行档位”：用户选择 → 配置落盘 → 调度读取 → 预算检查 → 产出说明 → 可恢复执行。

必须拆开三个维度：

| 维度 | 回答的问题 | 示例 |
|---|---|---|
| 研究目标／任务类型 | 做什么、用于什么 | 开题背景、方法选型、证据抽取、争议核验 |
| 执行深度 `execution_depth` | 本次做多少、核验到哪一层 | `quick`、`standard`、`deep` |
| 交互方式 `interaction_mode` | 如何确认参数 | `interactive`、`headless` |

因此，“D1 选择开题／系统综述”不能等价于“用户选择深度模式”。开题可以先快速摸底，随后再做深度检索。反过来，单个方法选型也可以要求深度核验。

建议中文统一使用“快速／标准／深度”；“中等”作为“标准”的输入别名，不再创建第四种值。

## 2. 当前框架的真实接入点与风险

以下是本次本地源码核对结果，路径相对于项目根目录。

| 现有位置 | 已核实行为 | 接入时必须处理 |
|---|---|---|
| `skills/literature-discovery-acquisition/scripts/agent_search.py` | `--mode` 只有 `quick/deep`，默认 `deep` | 增加标准档的真实策略；不能把脚本默认值当作用户确认 |
| `shared/grill_me/dimensions.py` | 分别提供检索、抽取、综合问询维度 | 提供共享深度维度，保留原有 D/E/S 编号 |
| `shared/grill_me/response_parser.py`：`select_questions()` | 首轮问题上限为 5，候选维度被截取 | 深度问题不能简单追加末尾而被挤掉 |
| 同文件：`_check_unresolved_critical()` | 检查传入的已展示问题 | 执行前另外检查全部必需维度，不能只检查本轮 |
| 同文件：`submit_response()` | 达到问询轮数上限后，对未决项采用推荐值并确认 | 执行深度必须排除这种静默回退 |
| 同文件：`bypass_headless()` | 缺失的 CRITICAL 维度存在推荐值回退 | 无人值守入口同样必须验证深度来源 |
| 同文件：`generate_snapshot_markdown()` | 标题固定包含 Research Gate Confirmed | 新增未决状态后，要按真实状态渲染标题 |
| `shared/grill_me/recommender.py` | 有基于任务模式／目标的快速倾向判断 | 推荐可以参考目标，但最终档位只能由有效选择确定 |
| `shared/context_resolution/context_resolver.py` | 已有上下文与来源解析体系 | 增加深度的来源、适用范围和冲突处理 |

推论：只修改 `SKILL.md` 加一句“询问执行深度”，仍可能出现“未展示、未回答、自动回退、脚本默认 Deep”的绕过路径。必须同时修改交互协议和运行入口。

## 3. 先定交互规则：什么时候问、什么时候不问

### 3.1 必须问的情况

当前任务未明确指定深度，且没有适用于本次运行的已确认配置时，必须提供选择。推荐项是标准档，但“推荐”不等于“已同意”。

建议将共享维度命名为 `EXECUTION_DEPTH`，显示名称为“执行深度与资源投入”。不要挪用 D1，也不要重新编号所有既有维度。

推荐第一轮同时展示研究目标和执行深度；给深度预留一个问题位置。若其他参数已经齐全，只问深度一个问题，不为满足“3–5 问”而补无关问题。

界面应说明每档的覆盖范围、核验程度、预计资源和交付差异。尚无测量数据时明确写“时间／Token 待校准”，不能假装有可靠估计。

### 3.2 可以不再问的情况

1. 用户本次明确说“使用标准模式”；记录为当前用户选择。
2. 同一流水线已有用户确认的执行配置；下游展示“沿用本次流水线标准档”，不重复追问。
3. 用户主动指定本次使用某份配置文件，该文件明确给出了档位。
4. 用户事先设置了有效的项目偏好；展示采用的偏好，允许覆盖，并保留来源。

仅仅在 README、论文附件或旧报告中搜到“Deep”，不属于上述情况。项目资料中的描述不是用户授权。

### 3.3 “按推荐”的严格含义

- 当前已展示的选项包含深度，用户回答“全部按推荐”：可以确认标准档。
- 当前只展示 D1，用户回答“按推荐”：只能确认研究目标，必须继续问深度。
- 用户此前在另一任务说过“按推荐”：不能套用到新任务。
- 用户只回答一个选项字母：按本轮已展示问题解析；多个问题下存在歧义时不得猜测。

记录 `question_set_id`，将回答绑定到实际展示的问题集合；不能把第一轮的选项编号解释成第二轮的另一问题。

## 4. 三档具体改变什么

### 4.1 所有档位不变的底线

不能编造引用；不能用摘要冒充全文证据；必须保留来源和定位；必须标注未知、未完成和不可比；不能为了速度绕过证据等级、隐私限制或合法全文获取边界。

快速档减少处理范围，不降低已报告事实的证据要求。深度档增加覆盖与复核，不自动保证结论正确。

### 4.2 三个 Skill 的操作差异

| Skill | 快速 | 标准 | 深度 |
|---|---|---|---|
| 检索与获取 | 核心概念、少量适配来源、有限候选池；记录明显缺口 | 概念矩阵、多来源补缺、有限引文扩展、覆盖记录 | 多轮缺口驱动扩展、前后向引文追踪、反证检索、饱和度评估 |
| 解析与抽取 | 约定的核心论文和字段；定位相关原文并核验 | 约定核心集的完整 Schema，处理相关表格、补充材料和冲突 | 增加关键图表核查、跨页／补充材料对照、数值一致性检查和高风险二次核验 |
| 跨文献综合 | 少量核心主张，给出初步支持／反对及限制 | 完整主张—证据矩阵、可比性分层、研究依赖去重、主要争议 | 系统反证搜索、亚组与边界分析、敏感性分析；满足条件才做定量综合 |
| 共同交付 | 简报＋证据定位＋未覆盖清单 | 标准报告＋结构化证据＋覆盖清单 | 审计型报告＋扩展轨迹＋敏感性结果＋未解决问题 |

独立复核必须有独立执行过程或人工复核证据。同一段输出改写一遍不能称作独立验证。复杂图表工具不可用时，列入待人工核验，不可假称深度档已完成。

### 4.3 可直接用于试运行的策略起点

下表是待校准的工程初值，不是现有性能结果，也不是普适研究标准。数量均是上限，不是强行凑满的目标。

| 策略参数 | 快速 | 标准 | 深度 |
|---|---:|---:|---:|
| 初始查询变体上限 | 3 | 8 | 16 |
| 引文扩展最大轮次 | 0 | 1 | 3 |
| 候选记录处理上限 | 50 | 200 | 600 |
| 首批全文处理上限 | 5 | 20 | 50 |
| 首批综合主张上限 | 3 | 10 | 20 |
| 高风险字段复核 | 进入报告前核验或标记未决 | 同左，增加跨位置一致性检查 | 同左，增加独立复核队列 |
| 覆盖缺口主动补查 | 记录后结束 | 1 轮 | 最多 3 轮，满足停止条件可提前结束 |

这些参数应存放于配置，不散落在提示词中。批次完成不代表整个研究任务完成。例如用户要求处理 100 篇论文，快速档首批完成 5 篇时必须报告剩余 95 篇，不能静默将需求缩为 5 篇。

时间和 Token 是另一组预算约束，不能仅凭论文数换算；扫描件、长补充材料和复杂图表的成本差异很大。

## 5. 建立共享执行配置

建议新增以下文件；本节列出的新增路径目前属于实施计划：

```text
shared/execution/
  __init__.py
  profiles.py          # 三档策略与版本
  selection.py         # 选择来源、别名、确认规则
  budget.py            # 预算预留、结算、停止
  preflight.py         # 入口一致校验
schemas/execution_profile.schema.json
tests/test_execution_depth.py
tests/test_execution_budget.py
```

统一数据结构示例（拟新增，不可直接视为当前 Schema 已支持）：

```json
{
  "schema_version": "1.0",
  "profile_version": "depth-v1",
  "run_id": "example-run-001",
  "execution_depth": "standard",
  "interaction_mode": "interactive",
  "selection": {
    "status": "confirmed",
    "source": "current_user",
    "scope": "pipeline",
    "question_set_id": "stage0-round1",
    "selected_value": "standard"
  },
  "stage_overrides": {},
  "budget": {
    "token_limit": 90000,
    "active_seconds_limit": 1800,
    "finalization_reserve_fraction": 0.1,
    "enforcement": "best_effort"
  }
}
```

这里的 90,000 Token 和 1,800 秒只是配置形状示例，不是标准档的性能承诺。部署者必须明确设定预算；首次校准前也可以使用 `null` 表示没有该项数值限制，但界面必须显示“未设置”，不得显示“受硬上限保护”。

Schema 至少约束：

1. 档位枚举只允许 `quick/standard/deep`，输入“中等”先归一化。
2. 预算数值为正数或显式 `null`；预留比例在 0 与 1 之间。
3. `selection.status` 区分 `unresolved/confirmed`；默认档位不自动生成 confirmed。
4. 阶段覆盖只允许 discovery、extraction、synthesis，且同样验证值与来源。
5. 禁止未知字段悄悄生效；与现有 JSON Schema 校验风格保持一致。
6. 配置绑定运行和策略版本。过期配置、其他研究任务配置不自动继承。

## 6. 修改问询引擎：解决“不问也执行”

### 6.1 注册共享深度维度

在 `shared/grill_me/dimensions.py` 新增公共构造函数，并由三个维度工厂调用，避免复制三份定义。

使用现有 `GrillDimension`、`DimensionOption` 数据结构，设置：

- ID：`EXECUTION_DEPTH`。
- 优先级：`CRITICAL`。
- 选项值：quick、standard、deep。
- 推荐项：standard。
- 类别：execution。

推荐新增兼容字段 `requires_explicit_selection: bool = False`；仅深度等需要明确确认的维度设为 True。旧维度保持原行为，避免无关重构。不要依赖 `default_value=None` 单独防回退，因为现有引擎仍可以取推荐项。

### 6.2 保证首轮问得到

修改 `select_questions()`：

1. 先解析当前用户明确选择和本次有效配置。
2. 未确认深度时，将该维度放入必展示队列。
3. 再安排其他未决 CRITICAL，随后才是 HIGH_IMPACT。
4. 保持单轮最多 5 问；剩余必需问题进入后续队列。
5. 即使没有生成问题，也必须通过全局 preflight 才允许 CONFIRMED。

不要把普通 `inferred_values["EXECUTION_DEPTH"]` 当成已确认选择。这里需要验证来源和确认状态，而不只是字典里存在一个值。

### 6.3 确认时检查全部必需项

保留解析器对本轮回答的解析职责；在引擎层增加对 `all_dimensions` 的完整校验。

伪代码如下，表达设计意图，不是可直接复制运行的补丁：

```python
parsed = parse_visible_answers(answer, active_questions)
resolutions.update(parsed)
missing = validate_all_required(all_dimensions, resolutions)

if missing:
    return input_required(missing)  # 不执行检索、下载或模型调用

profile = resolve_confirmed_profile(resolutions, run_context)
preflight(profile)
return confirmed(profile)
```

“存在 resolution”不等于“有效”：还需检查枚举、来源、适用范围以及当前题目绑定。任意自由文本不能直接成为 execution_depth 的合法值。

### 6.4 两轮以后怎么办

现有轮数上限可以保留为交互控制，但不能作为自动同意的理由。

- 普通允许默认的维度：保留原回退策略。
- `requires_explicit_selection=True`：保持未决，返回新增的 `INPUT_REQUIRED` 状态或等价结构。
- 停止主动循环追问，等待用户补充；不能无限重问，也不能自行启动工作。
- 快照显示“待确认”，不得继续使用固定的 Confirmed 标题。

若需要新增状态枚举，同步更新 `state_model.md`、快照渲染和状态消费者，避免只有文档认识新状态。

### 6.5 Headless 也不能绕过

修改 `bypass_headless()`：先校验明确参数或用户指定配置，再创建确认记录。缺失深度时返回结构化错误，建议 CLI 退出码为 2：

```json
{
  "status": "INPUT_REQUIRED",
  "missing": ["execution_depth"],
  "message": "请显式提供执行深度，或指定包含执行深度的配置文件。"
}
```

无人值守模式不调用交互工具。用户明确设定的项目默认值可以作为配置来源，但不能伪装成当前用户手选。

## 7. 解析自然语言与继承关系

在 `shared/context_resolution/context_resolver.py` 和相关规则中增加明确表达识别：

- “这次用快速模式” → quick。
- “中等深度运行” → standard。
- “检索深度、抽取标准、综合标准” → pipeline 默认值加三个明确阶段设置，或完整阶段映射。

必须加入反例：

- “深度学习文献”不能触发 deep。
- “快速检测方法”不能触发 quick。
- “标准差的提取”不能触发 standard。
- “不要用深度模式”只能排除 deep，不能擅自选 quick。
- 论文中的“采用 Deep 模式”属于材料内容，不是用户指令。
- 用户问“深度模式是什么意思”不是选择深度模式。

来源优先级建议：本次明确覆盖 > 本次明确阶段配置 > 本次已确认流水线配置 > 用户主动设置且有效的项目偏好。冲突且无法判断哪个是最新明确指令时，返回待确认。

## 8. 让模式真正影响脚本，而不是只影响写作长度

### 8.1 检索入口

修改 `skills/literature-discovery-acquisition/scripts/agent_search.py`：

1. 新增 `--execution-depth`，三个合法值，解析默认值为 None。
2. 保留 `--mode quick/deep` 作为兼容别名；只有调用者显式传入时才转换。
3. 两个参数同时存在且冲突时失败，不静默覆盖。
4. `standard` 必须加载独立的查询／扩展／候选上限配置，不可暗中映射为 deep。
5. 将解析后的配置传入真正执行查询、分页、引文扩展和下载的函数。
6. 对现有引擎尚不支持的策略返回能力缺口；不能只在输出里写“已深度检索”。

建议实施后支持以下调用；当前版本尚不支持此新参数：

```powershell
python skills/literature-discovery-acquisition/scripts/agent_search.py -q "研究主题" --execution-depth standard --output result.json
```

旧命令显式 `--mode deep` 可以继续工作并记录 legacy alias。旧命令不传模式的情况，必须明确选择迁移政策：推荐报缺少深度；如短期保留旧默认行为，应仅放入显式启用的兼容模式并告警，不适用于新流水线入口。

### 8.2 抽取入口

不要将 Extract/Audit 等任务类型替换成三档。应组合使用，例如“任务=Audit，深度=standard”。

调度层至少消费：本批论文上限、字段范围、相关表格／补充材料处理策略、高风险复核策略、资源余额。

如果主要由宿主 Agent 执行，应在 Stage 0 之后输出机器可读计划与检查清单，由 Agent 按计划调用辅助脚本。单个抽取脚本不承担整个流水线预算；统一控制放在调度层。已有脚本若尚无配置入口，先加薄适配层，不要求大规模重构所有脚本。

### 8.3 综合入口

同样保留争议扫描、学派图谱、主张审计等任务类型。深度影响主张范围、补查轮数、复核和敏感性分析，不改变证据是否可比的判定规则。

快速档仍需过滤重复研究、检查可比性。没有可比的效应量时，深度档也不能强行合并出一个数值共识。

## 9. Token 和时间预算的正确实现

### 9.1 区分两种运行环境

| 环境 | 可做什么 | 不应承诺什么 |
|---|---|---|
| 自己控制模型请求的执行器 | 读取服务方 usage，请求前预留，结算与限流 | 在未验证所有调用都受控前宣称总预算绝不超限 |
| 宿主 Agent 调用 Skill | 控制文献数、工具轮数、阶段计划；有 usage 才计实数 | 只靠 Markdown 提示词保证宿主全局 Token 硬上限 |

Skill 本身不是独立计费单元。宿主上下文、重试、推理和工具回传可能进入消耗。无法观察的部分必须标为 unknown，不填 0。

### 9.2 预算状态与检查时机

共享 budget 对象至少维护 limit、used、reserved、remaining。每次新增模型请求或工作批次前先检查，再执行，最后按实际使用结算。

```text
可启动额度 = 总上限 - 已用量 - 在途预留量 - 收尾预留量
```

并行任务需要原子预留，否则多个任务可能同时读到同一份余额。失败重试照样记账；已收费失败请求不能因为没有结果就抹掉。

输出长度上限不等于总 Token 上限。服务方用量字段若含缓存或推理子项，按其定义计数，不能将已经包含在 total 中的子项重复相加。保留原始 usage 以便复核。

只有在全部模型调用可拦截、输入与输出有可靠上界、并发预留有效时，才可以标记 `enforcement=hard`；否则使用 `best_effort`。

### 9.3 时间定义

- `wall_seconds`：从开始到当前的总墙钟时间，包含等待用户。
- `active_seconds`：排除暂停和等待用户后的执行墙钟时间，用于本手册的时间预算。
- 并行阶段的 active_seconds 不简单相加作为整体时长。
- 网络请求配置超时；接近截止时不启动超长批次。无法取消的在途调用可能产生有限超时，报告实际超出量。

### 9.4 预算耗尽后的行为

停止新任务 → 保存已完成结果和待办 → 执行预留的必要收尾 → 输出 `partial` 与停止原因。

不能静默增加预算，也不能将深度档中断后自动改名为“快速档已完整完成”。保留 requested_depth=deep，同时报告实际完成范围。

资源状态和研究状态必须分开：`budget_exhausted` 不等于“证据饱和”；查询无新增也不必然等于领域无更多文献。

## 10. 三个 Skill 共用一次选择与一份总预算

首个 Skill 确认配置后，生成运行级配置文件。下游通过路径或运行 ID 读取，不从自然语言报告里猜档位。

建议每次运行目录保存：

```text
runs/<run_id>/
  execution_profile.json
  protocol_snapshot.md
  usage_ledger.jsonl
  execution_receipt.json
  pending_work.json
```

这些是拟新增输出，不是当前既有文件。记录写入应避免中断后出现半份配置；恢复运行时先验证运行 ID、配置版本与完整性。

预算可按阶段分配，但分配总和加收尾预留不得超过总额度。未使用额度可按明确策略流转；阶段切换不能重新获得一整份总预算。

如果用户提出“检索深度，抽取与综合标准”，仅覆盖指定阶段。阶段提高深度并不自动增加总预算；若原额度不足，展示预期未完成范围并请求是否追加。

从快速升级到深度时，复用已核验记录和文档缓存，继续补足缺口。复用前检查研究问题、纳排标准、文档版本和 Schema；目标改变后旧筛选结果不能直接当作当前有效结果。

独立启动下游 Skill 且没有本次配置时，照常询问深度；不要因为它拿到了某份上游报告，就默认上游资源选择永久有效。

## 11. 同步三个 Skill 的操作说明

分别修改三个 `skills/<skill-name>/SKILL.md` 及其 `references/stage0_grill_me.md`，添加相同的最小入口规则：

> 执行前独立确认 execution_depth；研究目标不能替代深度选择。未指定且无有效配置时必须展示快速／标准／深度的工作范围与资源差异。未确认不得启动研究执行。下游沿用同一运行的已确认配置。所有档位保留证据和审计底线；预算不足时输出部分结果及待办，不自动扩额。

同时更新：

- `shared/grill_me/core_protocol.md`、`state_model.md`、`protocol_snapshot.md`：确认与未决状态。
- `shared/grill_me/recommendation_policy.md`：标准可推荐、不可静默选定。
- `shared/context_resolution/` 内相关来源与冲突规则：哪些来源能确认深度。
- `shared/core/cross_skill_contract.md`、`schemas/scholarflow_contract.md`：运行级配置传递与兼容。
- 安装与打包路径：保证新增共享文件进入安装产物。

若三个输出 Schema 对未知字段有限制，不能直接塞入 execution_profile。优先使用独立运行级配置；确有需要时新增版本化引用字段，并同步 producer、consumer、fixtures 和 roundtrip 测试。

## 12. 快照与最终回执必须显示什么

开工前快照至少包含：研究目标、任务类型、所选深度、选择来源、适用阶段、策略版本、预算、预算执行能力、预计交付及缺口。

最终回执建议包含：

```json
{
  "run_id": "example-run-001",
  "requested_depth": "standard",
  "status": "partial",
  "stop_reason": "active_time_limit",
  "usage": {
    "tokens": null,
    "token_measurement": "unavailable",
    "active_seconds": 1800
  },
  "completed_scope": ["核心查询", "首批证据抽取"],
  "pending_scope": ["引文补查", "部分表格核验"],
  "limitations": ["宿主未提供可观测的模型Token用量"]
}
```

示例仅说明格式。不能把估算 Token 写入实测字段；预测另存 estimate 与校准版本。仅观察到部分调用时，用 partial measurement 并说明覆盖范围。

## 13. 实施顺序：拆成五个小任务

### 任务一：锁定契约和交互

新增深度枚举、配置 Schema、公共维度、确认政策；写“D1 已答但深度未答”的失败用例。此阶段先不改变检索算法。

完成条件：三个 Skill 都能展示或正确继承深度，未确认绝不能进入执行。

### 任务二：修复所有绕过入口

修改 select_questions、submit_response、headless、快照标题和自然语言来源识别。增加公共 preflight，所有研究执行入口都调用。

完成条件：超过 5 个必需问题、轮数耗尽、默认 Deep、自由文本非法值都无法绕过确认。

### 任务三：接入三档实际策略

先接检索，再接抽取，再接综合。每接一段，用假工具记录实际调用，检查档位是否改变查询／批次／复核流程，而不仅是报告标题。

完成条件：同一输入下三档执行计划不同；必需证据约束不变；不支持的能力被如实报告。

### 任务四：预算、回执与断点续跑

先做工具轮数与处理量预算，再做可观测的 Token 记账、时间控制、并发预留和配置继承。宿主不可观测部分保留诚实边界。

完成条件：耗尽后保存 partial；下游不重置总额度；恢复不重复扣已结算用量。

### 任务五：安装验证与真实校准

同步文档、Schema、打包文件，在独立临时目录安装并进行冷启动测试。明确运行的是仓库版本还是用户已安装版本，避免“源码已改、宿主仍加载旧 Skill”。

完成条件：新会话只加载安装后的产物，也能正确展示深度并执行对应策略。

## 15. 如何给用户显示可信的时间／Token预估

不要先写死“快速 5 分钟、深度 30 分钟”。先用一组固定任务做三档对照，至少覆盖短文、长文、扫描件、复杂表格和不同候选池规模。

固定模型、工具版本、任务输入、缓存状态和资料快照，记录：

- 研究质量：相关文献覆盖、抽取准确率、原文定位正确率、无支持主张率、限制披露。
- 资源：输入／输出／可观测推理 Token、调用次数、执行时长、失败重试。
- 运行条件：论文数、页数、OCR比例、网络与缓存状态。

区分冷缓存和热缓存。初测数据只用于调参数；另留未参与调参的任务作验证。可以先做每档 10 次探索性运行，但这种小样本不足以宣传稳定性能。

有足够数据后，界面显示相似任务的中位数和区间，并注明模型、样本量和估计条件。任务规模改变时重新估计，不能把每篇论文成本直接当作整个流水线成本。

预期通常是 quick < standard < deep 的资源投入，但单次因缓存、超时或资料复杂度可能不严格单调。验收关注策略和总体测量分布，不强迫每次深度档都比标准档更慢。

## 16. 可交给开发 Agent 的实施任务说明

以下是实施时可使用的任务说明，不表示本次已授权执行源码修改：

> 基于当前 ScholarFlow 仓库实现统一 execution_depth，支持 quick/standard/deep，中文快速/标准/深度，中等为标准别名。先读取本手册及现有源码，核对版本差异。保留研究目标、任务类型和交互方式的独立性。不重排 D/E/S 维度编号。新增共享配置和公共深度维度，确保首轮展示、所有必需项全局校验、轮数耗尽不自动确认、Headless 缺参明确失败。把确认后的策略接入三个 Skill 的真实操作，记录版本、来源、预算和结果范围。无宿主 usage 时不得承诺 Token 硬上限。增加回归、并发预算、负面解析和安装后测试；不调用收费服务、不上传私人资料，除非另有明确授权。分五个小任务实施，保留无关工作区修改；最终列出实际实现、通过测试、仍依赖宿主的限制。

## 17. 最小可用版本的边界

优先交付“必问或有效继承 + 三档实际策略 + 未完成清单 + 安装验证”。随后再完善 Token 仪表和性能估计。

但在仪表未完成时，必须明确：已有三档范围控制，不等于已有精确成本控制；已有深度执行策略，不等于已经证明能力优于其他科研 Agent。

执行深度的价值，是让用户清楚选择本次投入，并能核对系统是否真的按选择执行，而不是给同一流程换三个标签。
