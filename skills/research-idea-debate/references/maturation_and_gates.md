# 想法成熟度与阶段门 (Maturation & Gates)

> 加载时机：判断"现在能不能做评估性提问"、或用户提出反对意见需要定性时读取。

## 一、三个维度互相独立

`maturation`（成熟度）、`epistemic_status`（证据状态）、`disposition`（处置）**互相独立，不互相派生**。

| 维度 | 取值 |
|---|---|
| `maturation` | `RAW` / `DEVELOPING` / `TESTABLE` |
| `epistemic_status` | `INTUITION` / `HYPOTHESIS` / `EVIDENCE_SUPPORTED` / `EVIDENCE_CHALLENGED` / `UNRESOLVED` |
| `disposition` | `ACTIVE` / `RETAINED` / `REVISED` / `REJECTED` / `DEFERRED` |

**最容易出错的组合**：因不可行而搁置（`DEFERRED`）**不等于**科学上被否定，不得写成 `EVIDENCE_CHALLENGED`。

## 二、阶段门：允许与禁止

| 阶段 | 判定特征 | 允许的下一步 | 明确禁止 |
|---|---|---|---|
| `RAW` 原始直觉 | 只有兴趣、观察或模糊倾向，尚无可陈述的命题 | 澄清、给出候选表述、举对照例、增加一个可区分差异、**前提审查（P2）**、**提出替代解释（P4）** | 判定成立与否、要求可证伪形式、做正反裁决 |
| `DEVELOPING` 发展中 | 已有可陈述命题，但前提、预测或替代解释不完整 | 前提审查、补预测、生成替代解释、寻找边界 | 要求完整验证方案；以"不完整"为由否定 |
| `TESTABLE` 可检验 | 命题有明确对象、条件与至少一个可观察预测 | 构造最小判别设计、找反例、比较替代解释 | 把设计草案当作已执行结果 |

## 三、发展配额（防过早否定）

- `RAW` 阶段须先积累 **2 个发展信号**，才能进入 **P3**（首次要求给出可观察预测／可证伪形式）。
- **P2 前提审查与 P4 替代解释属生成性动作，可在 `RAW` 阶段先行**，不因命题尚未成形而被阻止。
- 发展信号**只认这四类**（见 [convergence_and_recovery.md](./convergence_and_recovery.md) 第一节）：
  `INTUITION_FORMULATED`（命题成形）、`QUESTION_SHARPENED`（问题收窄）、`PREMISE_SURFACED`（隐含前提显式化）、`DISCRIMINATION_ADDED`（新增可区分差异）。
- `ALTERNATIVE_ADDED`（补了一条替代解释）**不计入**——它不改变原命题本身的可检验性。
- 配额用尽但仍无可陈述命题时，**不判"不成立"**，而是记为未决并询问用户是否换角度；连续两次如此触发 S1。
- **配额检查由确定性程序在每轮结束后执行，不依赖自检。** 实测中主持人自检曾漏过打包提问。

## 四、成熟度历史的不变量

`maturity_history` 必须满足：

1. 从 `RAW` 开始（`hist[0].from == "RAW"`）；
2. **逐级连续**：每一段的 `from` 等于上一段的 `to`；
3. **不得跳级**：只能 `RAW → DEVELOPING → TESTABLE`；
4. 终点等于当前 `maturation`；
5. 无历史时 `maturation` 只能是 `RAW`；
6. **只升不降**；用户修订命题导致回落时必须记录回落理由。

## 五、反对意见的定性（三选一，互斥）

| 定性 | 含义 | 强制要求 |
|---|---|---|
| `FATAL` | 命题在当前形式下不可能成立 | **必须给出逻辑矛盾或已知事实依据** |
| `ADJUSTABLE` | 可通过限定条件、改口径或补设计修复 | **必须给出具体改法**；只写"存在问题"不允许结轮 |
| `UNRESOLVED` | 当前信息不足以判断 | 转入未决或查证，**不得**写成否证 |

## 六、steelman 要求

- 评估必须针对命题的**最强版本**。
- 若为便于讨论而替换成简化版，必须显式标注：**"以下讨论的是简化版 X，不是你的原话。"**
- 复述用户命题时不得润色强化或弱化；若整理成书面形式，须标注"由用户口述整理"并保留原始表达。

## 七、内部一致性守卫（不含新证据）

每轮可自检，不需要外部检索：

| 守卫 | 要求 |
|---|---|
| **命题身份保持** | 焦点问题必须引用某个 `idea_id@version`；修订后重问旧版本内容视为错误 |
| **资源可行性** | 提出方案前核对用户已声明的资源与时间窗；超出时标"超出已知资源"并询问，不默认可行 |
| **逻辑一致** | 同一会话内两条命题互相矛盾时必须显式指出并提请用户裁决，不静默替换 |
| **禁止伪造证据** | 任何未被引用的数据、文献、参数一律标"待补"或"待验证"，不得用看似合理的数值填空 |

## 八、模式与推进路径

| 模式 | 路径 | 最重要的进展信号 |
|---|---|---|
| `explore` | 含糊 → 候选表述 → 差异化 → 最小区分 | `INTUITION_FORMULATED`、`DISCRIMINATION_ADDED` |
| `examine` | 命题化（性质 + 基准）→ 承重前提 → 反例 → 替代解释 → 判别方案 | `PREMISE_SURFACED`、`DISPOSITION_DECIDED` |

**命题性质决定允许的判定类型**（`examine` 首轮必须明确）：

| 性质 | 允许的判定依据 | 禁止 |
|---|---|---|
| 描述性 | 观测记录、抽样设计 | 用机制推理替代观测 |
| 关联性 | 相关性证据、混杂控制 | 表述为因果 |
| 因果性 | 干预、对照或充分排除性论据 | 仅凭共变升级为因果 |
| 方法选择 | 目标量、误差结构、成本 | 抽象比较"哪个更好" |
| 价值取舍 | **由用户决定** | 伪装成经验事实裁决 |

## 九、收尾前检查

进入 `CHECKPOINT` 前核对：本会话是否**至少一次进入 P3**？

- 未进入 → 命题仍在 `DEVELOPING`，小结中**不得**出现"最小验证方案"或"命题已可检验"。
- 只能写："尚未形成验证方案，缺的是哪一步（哪条预测或哪个改判条件）。"
